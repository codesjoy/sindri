# 工程规范（通用）

## 1. 适用范围与技术栈

本规范适用于采用 Go、Yggdrasil、Protocol Buffers 和 PostgreSQL 的多服务项目，只定义跨项目工程规则。具体产品的安全域、服务清单、资源模型、数据库
owner 和协议流程由项目架构文档决定。

本节记录目标架构的统一技术选型，不表示所列依赖均已在当前实施阶段接入。依赖版本以各项目的 `go.mod`
、生成工具配置和发布基线为准，本规范不固定补丁版本。

### 1.1 技术栈

| 领域       | 选型                                                                   | 说明                                                                       |
|----------|----------------------------------------------------------------------|--------------------------------------------------------------------------|
| 语言       | Go                                                                   | 服务、共享库、生成工具和运维 CLI 的主要实现语言                                               |
| 应用框架     | `github.com/codesjoy/yggdrasil/v3`                                   | Runtime、Config、RPC/REST Server、BackgroundTask 和模块化                       |
| 依赖注入     | `github.com/google/wire`                                             | 代码生成式 DI；由项目生成门禁重建并检查生成结果                                                |
| ORM      | `gorm.io/gorm`                                                       | model 和 repo 实现在 `data/`；`gorm.io/driver/sqlite` 仅用于不依赖 PostgreSQL 语义的测试 |
| 缓存       | `github.com/redis/go-redis/v9`                                       | Redis 客户端；`github.com/alicebob/miniredis/v2` 用于单元测试，不把 cache 作为事实源       |
| RPC/REST | `protoc-gen-yggdrasil-rpc`                                           | 根据 Proto 服务生成 RPC                                                        |
| Proto 校验 | `buf.build/go/protovalidate`                                         | 字段和消息约束在 Proto 中声明，由服务端统一执行                                              |
| 可观测性     | OpenTelemetry（OTLP）、`github.com/prometheus/client_golang`、`log/slog` | logs、metrics 和 traces；敏感数据遵循统一脱敏规则                                       |

### 1.2 公共基础库

跨项目通用能力优先复用 `github.com/codesjoy/pkg/basic/*`。公共基础库只提供无业务所有权的基础设施能力，不承载产品资源、领域状态机或跨服务事实副本。

| 包                                           | 职责                                   |
|---------------------------------------------|--------------------------------------|
| `github.com/codesjoy/pkg/basic/xerror`      | 统一错误、稳定 reason 和 gRPC/REST 协议错误映射    |
| `github.com/codesjoy/pkg/basic/xgorm`       | GORM 初始化、连接配置和无业务所有权的数据库基础能力         |
| `github.com/codesjoy/pkg/basic/xredis`      | Redis 客户端配置、连接管理和通用观测封装              |
| `github.com/codesjoy/pkg/basic/transaction` | 事务抽象及 GORM 适配；业务事务边界由真正需要原子性的最小写路径决定 |

本项目的装配边界固定为：基础库负责通用技术能力；服务负责配置、依赖组装和 owner-specific 校验；shared
只承载跨服务领域语义、安全不变量、协议策略或真实基础设施适配器。服务需要 Redis、S3 或 Kafka 时直接在本地 Config 中保留底层完整配置和
Option，不建立会屏蔽能力的缩减适配器；S3/object store 等具有 immutable、URI 或资源关闭语义的适配器可以保留在
shared。业务幂等由具体服务使用唯一键、状态机或请求约束实现，不预先建立 owner-neutral 的通用存储模型。

## 2. 规范优先级

- 代码与文档冲突时，先确认规范性文档；不得以现有代码作为默认正确答案。

## 3. 仓库与生成代码

推荐目录：

```text
api/             Proto 和协议定义
gen/             生成代码，禁止手工修改
cmd/             每个可执行服务的入口
internal/        项目私有实现
pkg/             可跨服务复用、无业务所有权的库
migrations/      按数据库 owner 划分的迁移
configs/         服务配置
deploy/          部署与基础设施定义
tests/           顶层集成、端到端和安全测试（见 §12.1）
docs/            架构设计、详细设计、执行计划和工程规范
```

- `gen/` 必须可由仓库内声明的工具链重复生成。
- 生成命令执行后必须通过 clean-tree 或生成物差异检查。
- `internal/<service>` 不得被其他服务 import；跨服务调用只使用生成的私有协议客户端。
- 单个服务的集成测试放在 `internal/<service>/tests` 下，顶层 `tests/` 放整体集成与端到端测试（见 §12.1）。
- `pkg/` 只承载协议、密码学封装、事件基础设施等无主体所有权的能力。

### 3.1 目录命名

- 目录与文件路径按内容或职责命名，禁止用执行阶段、里程碑或迭代代号命名（如 `step1`、`phase2`、`milestone-a`）。
- 版本标识只能出现在文件内容或显式 `version` 字段中，不得出现在目录或文件路径里。
- `deploy/` 按部署方式划分（`deploy/docker`、`deploy/k8s` 等），不得以阶段代号命名。
- `internal/shared` 下的共享能力按领域聚合为单包目录（如 `shared/security`、`shared/storage`），不再按子能力逐个建顶层目录；空目录必须及时删除。

## 4. 服务和数据所有权

- 一个业务资源只能有一个 source of truth 服务和一个写入数据库 owner。
- 服务边界由项目架构确定，禁止为了代码复用合并不同安全域。
- 服务不得直接访问其他服务的数据库、表、迁移版本或 ORM model。
- 跨服务读取只能通过私有 API、以私有 API 为权威回源的有界 cache、领域事件构建的只读 projection，或明确批准的离线分析链路。
- 所有关系数据库只允许普通物理表，不得定义外键、普通视图、物化视图、用户 trigger、stored procedure 或 rule；数据库 owner
  之间也不得共享写事务。

## 5. Go 服务结构

每个进程使用 `cmd/<service>/main.go` 作为入口，由 Yggdrasil Runtime 加载配置、RPC、REST 和后台任务。

推荐分层：

| 层         | 职责                                | 禁止事项              |
|-----------|-----------------------------------|-------------------|
| `app`     | 配置字段注入、依赖装配、生命周期、服务注册             | 承载领域不变量           |
| `biz`     | 聚合、UseCase、Repo 接口、领域事件           | 依赖数据库或传输层实现       |
| `data`    | PostgreSQL repo、外部客户端、事务实现        | 绕过 UseCase 暴露写操作  |
| `service` | RPC/REST handler、resource name 转换 | 直接拼接非参数化 SQL      |
| `conf`    | 进程配置组合、Runtime 加载、默认值协调、聚合校验      | 依赖 `app` 或承载业务不变量 |

- 依赖方向为 `service -> biz <- data`，由 `app` 装配。
- 事务只在需要原子提交的最小写路径开启；业务表与 outbox 需要原子提交时由 data repo 开启或复用事务。不得为所有 UseCase
  统一套事务，纯查询不得开启事务，handler 不得管理业务事务。
- handler 只负责协议校验、resource name 转换、调用 UseCase 和错误映射。
- Repo 和私有读取协议必须提供与公共 API 最大页大小匹配的批量读取接口。不得通过逐项 Get 组装集合响应。
- 禁止在 `for`、`range`、递归遍历或逐项 helper 中执行数据库、RPC、对象存储或其他远程 I/O。循环只允许进行内存收集、去重、校验、映射和组装。
- 集合请求的 I/O 次数必须与结果行数无关：一次主查询，加上每个显式 expansion 或依赖类型最多一次批量查询或
  BatchGet。不得通过循环分批调用绕过批量上限。
- 未完成的 RPC 不得注册到运行时。嵌入生成的 `Unimplemented...Server` 只用于接口演进，不能作为已注册方法的行为。
- 启动时必须验证数据库连接、密钥引用、issuer、内部服务身份，以及已声明的 projection readiness 或 cache 权威回源配置。

### 5.1 配置所有权与依赖注入

- `data`、`service`、`consumer` 和 `task` 分别定义自身构造所需的最小配置类型；该类型可以包含 `mapstructure`
  标签，因为它属于进程内部的配置契约。
- 服务的 `conf.Config` 是进程级组合根，可以组合上述实现包的配置类型，并负责 Runtime 解码、默认值协调、模块校验和跨模块校验。
- 实现包和 `biz` 不得反向 import 所属服务的 `conf` 包；构造器不得接收或保存整个 `*conf.Config`，只能接收自身配置或必要的独立字段。
- `conf` 不得依赖 `app`；`app` 同时依赖 `conf` 和具体实现，是配置字段进入 Wire provider、构造器和生命周期对象的唯一装配位置。
- 配置完成加载和校验后视为不可变。构造器接收配置指针时只能读取，不得在注入后修改默认值、切换配置或写入运行时状态。
- 底层库采用 `Option` 构造模式时，应用应定义 Wire 可注入的 `Config`，由 provider 在内部映射为 options；Config 必须允许保留完整底层
  options，不得用少数字段封装屏蔽底层能力。
- 同一进程存在多个相同底层类型的配置时，必须使用不同的命名类型或显式 provider，保证 Wire 按类型注入时没有歧义。
- 依赖方向固定为：

  ```text
  app -> conf -> implementation Config
  app -> data/service/consumer/task -> biz
  ```

  以下方向禁止出现：

  ```text
  data/service/consumer/task/biz -> conf
  ```

- 配置声明若需要跨项目复用，或直接依赖实现包会引入不合理的重量级依赖，应提取到不依赖业务实现的专用配置包；不得通过让实现包反向依赖应用
  `conf` 来解决循环依赖。

使用 Wire 时，`conf.Load` 已返回完整且经过校验的根配置，应使用 `wire.FieldsOf` 将其字段提供给实现方：

```go
// internal/<service>/conf/conf.go
package conf

type Config struct {
	DB   data.Config    `mapstructure:"db"`
	OIDC service.Config `mapstructure:"oidc"`
	Task task.Config    `mapstructure:"task"`
}
```

```go
// internal/<service>/app/wire.go
package app

var configSet = wire.NewSet(
	wire.FieldsOf(new(*conf.Config), "DB", "OIDC", "Task"),
)
```

`wire.FieldsOf` 用于拆分已经加载的根配置；`wire.Struct` 用于根据已有依赖新建一个结构体，不用于重新组装已经由 `conf.Load`
返回的 `conf.Config`。

使用 Wire 装配时遵循以下规则：

- 共享能力（`database`、`event` 等）的构造器定义在共享包内并直接作为 Wire provider 使用；服务 `app` 包不得对共享构造器再做同名包装（如逐服务复制
  `provideDatabase`）。
- `wire.Build` 由多个小 provider 组合而成；资源构造（建连接、建 task）拆为独立 provider，`provideBundle` 只做装配（注册
  task、hook），不内联资源构造逻辑。
- provider 只接收自身配置或必要字段，不得接收整个 `*conf.Config`；跨包依赖方向仍为 `app -> conf -> 实现`。
- 具有后端实现的基础设施适配器（对象存储等）必须接口与实现分离：抽象接口定义在不依赖任何后端（AWS/S3
  等）的独立包内，业务代码只依赖接口；具体实现留在独立包，仅由 Wire 注入时通过 `wire.Bind` 绑定到接口。不得让业务包因 import
  接口而传递依赖后端 SDK。
- `rt.Logger()` 已保证非 nil（缺省回退 `slog.Default()`），禁止再以 `provideLogger` 之类带 nil 判断与回退的 provider
  包装；基础设施构建方法（`event.Provide*` 等）接收 `yggdrasil.Runtime` 并在内部使用 `rt.Logger()`，`*slog.Logger` 不作为独立
  Wire 依赖出现。

### 5.2 代码注释

- 代码注释一律使用英文。
- 注释不得引用项目docs目录下的文档名或外链；文档与代码冲突时以规范性文档为准，但不在代码中点名文档。
- 注释只解释"为什么"和不可从代码直接看出的约束，不复述代码字面行为。

## 6. 错误模型

- 使用稳定的 gRPC code。只有调用方无法提前识别且必须采取特殊处理的领域冲突才提供稳定 reason；参数、name、field
  mask、不存在、非法状态和认证失败等已有标准 code 的错误不得重复包装 reason。
- 唯一约束冲突映射为 `ALREADY_EXISTS`，不存在映射为 `NOT_FOUND`，状态不允许映射为 `FAILED_PRECONDITION`，etag 冲突映射为
  `ABORTED`。
- 认证失败不得泄露账号是否存在、主体状态或具体凭据错误。
- 内部数据库、密钥和下游错误不得原样返回给外部调用方。

## 7. 数据库迁移

- 每个数据库 owner 使用独立迁移目录、DSN 和版本表。
- 迁移文件使用 `YYYYMMDDHHMMSS_description.sql`，包含明确 Up/Down 段。

## 8. 测试与发布门禁

禁止以跳过测试、注册空实现或临时共享数据库的方式满足发布门禁。

- **分层放置**：单元测试放在各实现层旁（`biz`/`data`/`service`/`consumer`/`conf`）；单个服务的组件测试放在该服务的 `tests`
  子包下（如 `internal/<svc>/tests`）；整体集成、端到端和安全测试放在仓库根目录 `tests/` 下。
- `tests/` 下的整体集成与端到端测试使用 testcontainers-go 拉起真实依赖（Postgres、Kafka、Redis 及兄弟服务），不得以内存替身替代。
- **单元测试分层与替身**：`biz`（聚合 + use-case）与 `data`（repo）用 in-memory sqlite 直接实例化 repo、miniredis 作 Redis
  替身，不 mock 自身的 repo 接口；`service`/`consumer` 是外部适配器，用轻量单测覆盖映射与 adapter
  自身逻辑（mask/路由/幂等/鉴权门禁/错误映射），可对外部依赖与非自身职责的下游用手写 fake；`conf` 单测覆盖配置校验。生产环境仍用
  Postgres，sqlite/miniredis 仅用于测试。
- **组件测试瘦身**：`internal/<svc>/tests/` 以外部测试包（`<service>_test`）通过公开 RPC 驱动
  service→usecase→repo→publisher 全链路，验证接线/契约/事件顺序/持久化往返，不重复 `biz`/`data`
  已覆盖的逻辑；仅当无法经公开入口触达的未导出纯辅助函数，才以内部测试形式留在实现包内并作为最小例外显式标注。
- **escape-hatch**：sqlite 仅用于不依赖 PostgreSQL 语义的测试；uuid PK 类型、timestamptz、`ON CONFLICT ... RETURNING`、unique
  nulls-not-distinct、JSONB、partial index、advisory lock 等 Postgres 特有语义须上移 `tests/` 用 testcontainers Postgres
  覆盖。
- **断言库**：测试优先使用 `github.com/stretchr/testify`（`require`/`assert`）；既有保留在 `biz`
  包内的标准库单元测试可维持原状，新增或迁移的测试一律使用 testify。
- **共享测试辅助**：跨服务复用的测试辅助（如 sqlite 初始化、录制型事件发布者）统一放在 `internal/pkg/tests`，不得在各服务测试包内复制粘贴。
